## 内容路径塌陷："点 opengel 哪篇都跳第一篇"

### 现象
`/cpp/opengel/*` 里点任意一篇，都打开 `三角形绘制`（该路径的第一条）。

### 根因（两层，缺一不可）
1. **@nuxt/content 的 path 生成把中文整段删掉**。
   `dist/module.mjs`：`const { pathMeta = {} } = nuxtOptions?.content?.build` →
   `generatePath` = `path.split('/').map(part => slugify(refineUrlPart(part), slugifyOptions))`，
   默认 `slugifyOptions = { lower: true }`。
   `slugify@1.6.9` 的默认 `remove` 正则 `/[^\w\s$*_+~.()'"!\-:@]+/g` 里 `\w` 只含 `[A-Za-z0-9_]`，
   **中文不属于 `\w` → 全被删**；另外 charMap 里 `$` → `dollar`，`+` 未映射所以被保留。
   于是大量文件塌成同一 path：opengel 13 篇 → `/cpp/opengel`；
   `C++的学习笔记`/`C++编译器思考`/`优雅和正确的使用C++的注释` → `/cpp/c++`；
   `C#的多线程`/`c#的流传输文件…` → `/csharp/c`；`Avalonia/合成渲染器` 等 5 篇 → `/csharp/avalonia`；
   `Vue学习笔记` 等一堆 → `/vue/vue`；`面试笔记.md` → `/`。
   `.path(route.path).first()` 永远命中第一条，这就是"总跳第一篇"。
2. **`route.path` 是 percent-encoded，库里存的是解码原文**。
   vue-router 的 `route.path` 保留编码（中文 → `%E4%B8%89…`，`+` → `%2B`），
   而 content 库 `path` 是解码后的原文；纯 ASCII 时两者恰好相等，所以只有中文/特殊字符 404。
   dev 日志里请求行就是 `/cpp/opengel/%E4%B8%89%E8%A7%A6...` 这种形式，可佐证。

### 修复
- `nuxt.config.ts` → `content.build.pathMeta.slugifyOptions.remove` 把 CJK 加回白名单：
  `/[^\w\s$*_+~.()'"!\-:@\u4e00-\u9fff]+/g`（顺手去掉 URL 里真会出事的 `# ? % &` 空格等）。
- `app/pages/[...slug].vue` → 查询前 `decodeURIComponent(route.path)`（用 `contentPath` 变量，try/catch 兜底）。
- 两处配合后：`/cpp/opengel/三角形绘制`、`/cpp/c++的学习笔记`、`/csharp/c的多线程`（title 仍是 `C#的多线程`）
  `/vue/dollarrouter和dollarroute的区别`（title 仍是 `$router和$route的区别`）全部可用。

### 验证
- sqlite（`.data/content/contents.sqlite`，node `--experimental-sqlite` 直读）：
  134 条记录 **重复 path = 0**；opengel 13 条路径各自唯一。
- HTTP：含中文/`+`/`$` 的 URL 由 404 → **200 且标题正确**；
  CDP 用应用 router 连续 `push` 三角形绘制→纹理→摄像机→Axios，title/h1 逐个正确 → SPA 跳转会重新取数。

### 结论：不需要改文件名
`+` 在真实链接里保持字面量、能正常匹配（只有我手工 `%2B` 编码才不匹配）；
`#` 被 slugify 清掉所以不进 URL。**文件名不必改**，`C#→c`、`$→dollar` 只是 URL 可读性略差。

## 静态部署（SSG）点任何文档都 404 — 根因与修复

**症状**：kiriyama.top 静态部署后点文档 404；纯 ASCII 名文档能开，含中文名的打不开。

**根因**：nitro.preset=static + prerender.routes: ['/'] + crawlLinks:true
→ Nitro 只能从首页顺 <a> 发现路由，而首页 useInfiniteList 的 PAGE_SIZE=10，
首屏 SSR 只渲染 10 条 → 只预渲染了 11 个页面（/ + 10 篇）。
证据：线上 /_nuxt/builds/meta/<buildId>.json 的 prerendered 数组正好 11 条。
其余 120+ 篇服务器上不存在 → nginx try_files 回退 index.html → 404。

**修复**（nuxt.config.ts）：
- 补上 nitro: { preset:'static', prerender:{ crawlLinks:true, routes:['/'], failOnError:false } }
  （本地配置里原本没有这段；用户贴的配置在构建机上）
- 新增 hooks: { 'nitro:init'(nitro) { nitro.hooks.hook('prerender:routes', ...) } }：
  从 .data/content/contents.sqlite 读 SELECT path FROM _content_content 全部加进预渲染列表，
  并手动加 '/'（routes.size>0 时 Nitro 不再自动补）。

## 服务器 SSG 构建失败（`/` 500 + 只预渲染 3 条路由）

**现象**（用户服务器 `/root/kiriyama_blog`）：`nuxi generate` → `Prerendering 3 initial routes with crawler`，
`/200.html` `/404.html` 正常，`/` 报 `[500] Server Error`，随后 `Exiting due to prerender errors`。

**已查实的机制（都在 node_modules 源码里）**：
- `3 initial routes` = Nitro 自带的 `/200.html` `/404.html`（`@nuxt/nitro-server` 的
  `if (nitro.options.static) nitro.hooks.hook('prerender:routes', …)`）+ 配置里的 `routes: ['/']`。
  **没有内容路由 ⇒ 那个枚举钩子在那台机器上没生效**（不是枚举结果为空）。
- `prerender:routes` 在 Nuxt 层也是公开钩子：`@nuxt/nitro-server` 里
  `nitro.hooks.hook('prerender:routes', (routes) => nuxt.callHook('prerender:routes', { routes }))`，
  类型声明在 `@nuxt/schema` 的 NuxtHooks：`(ctx: { routes: Set<string> }) => HookResult`。
  `nitro:init` 也确实被 `await nuxt.callHook('nitro:init', nitro)` 调用（两个钩子名都对）。
- **Nitro 会把真实错误吞掉**：`nitropack/dist/core/index.mjs:2115`
  `_route.error = new Error(`[${res.status}] ${res.statusText}`)`，
  `formatPrerenderRoute` 只打印 `route.error.message` → 所以日志里永远只有 `[500] Server Error`。
- **预渲染时 content 用的就是本地 sqlite 库**：`@nuxt/content/dist/runtime/internal/database.server.js:23`
  `if (import.meta.dev || ['nitro-prerender','nitro-dev'].includes(import.meta.preset)) return localAdapter(...)`
  → 路径是构建时固化的绝对路径 `<rootDir>/.data/content/contents.sqlite`，走 better-sqlite3。
  所以原生 sqlite 一坏 → 只有"会查内容的路由"（= `/`）静默 500，`/200.html` `/404.html` 照样成功。
- 新克隆下该库**会被构建写出来**：隔离副本（无 `.data` 起手）跑构建后
  `.data/content/contents.sqlite` 有 `_content_content` 134 行 → 枚举钩子读这个库是可靠的。

**修复方向**：钩子改为 try/catch 包住读数，失败就 `console.warn` 打印库路径 + 原因（不再静默）；
`existsSync` 判断去掉（一并删掉 `node:fs` 导入）。

**待用户回报**：服务器上
`node -e "const D=require('better-sqlite3');const db=new D('.data/content/contents.sqlite',{readonly:true});console.log(db.prepare('select count(*) n from _content_content').get())"`

## 「点卡片 → 404 / 落到 /cpp/opengel」根因：URL 与数据来自两份不同的内容库（已修）

### 现象（线上实测，Chrome CDP 真点）
- 首页 `<a href>` **全部正确**（`/cpp/opengel/光照贴图`、`/cpp/boost/cpp-boost`…，134 个锚点 134 条唯一）。
- 但真点一次 → `location` 变成正确路径、`<title>` 却是 `404 - Page not found | Nuxt`；硬刷新则正常。

### 根因（两层，缺一不可）
1. `nuxt.config.ts` 里有 `experimental.payloadExtraction: false`（非默认）。
   → 预渲染只把数据内联进 HTML，**客户端导航没有 `_payload.json` 可读**，于是 `useAsyncData` 在浏览器里重跑
   `queryCollection('content').path(...).first()`。
2. 客户端查询走 `@nuxt/content` 的 WASM sqlite，数据从 `GET /__nuxt_content/content/sql_dump.txt` 下载
   （`runtime/internal/api.js` → `database.client.js`）。**线上这份 dump 是旧构建的残留**：
   - 134 行只有 **68 个不同 path**、**0 条含中文**；13 篇 opengel 全塌成 `/cpp/opengel`（= 用户看到的"跳 /cpp/opengel"的来源）；
   - 行内 `checksum_content` = `v3.5.0--6VnUw…`，而线上构建的 `checksums.content` = `v3.5.0--LWMan…` → 两者不同源，可一锤定音；
   - 本地清干净重跑 `nuxi generate` 后，dump 内校验和与 `.nuxt/content/manifest.ts` **完全一致** → 证明"干净构建不会错位"，
     线上的错位是产物层面的残留（`__nuxt_content/**` 那份文件没被更新）。
- 于是：**URL 由构建期库生成（对）→ 点击后拿这个 path 去查运行时的旧库（错）→ 查不到 → `createError(404)`。**
  刷新正常是因为预渲染 HTML 里本来就带着数据，不需要查库。

### 修法（app 侧，一条配置；不依赖部署方"记得同步某文件"）
- 删掉 `experimental.payloadExtraction: false` → 用 Nuxt SSG 默认值：每篇文档的数据与页面**同一份产物**，
  预渲染到同目录 `_payload.json`，客户端导航读"这个 URL 自己的 payload"。
  URL 与数据从此**同源同一次构建**，不可能再出现两份库对不上。顺带客户端不再下载 1.68 MB dump + 1 MB WASM。
- `app/pages/[...slug].vue` 保持原样（`if (!page.value) throw createError(404)`），**不要**加"404 后整页重载"这种妥协兜底。

### 验证（本地 `nuxi generate` + 模拟 nginx `try_files` 的静态服务 + CDP 真点）
- 267 条路由、132 个 `_payload.json`（+ 根 `/`）；dump 内校验和 == manifest 校验和；134 锚点 134 唯一。
- 点 `/cpp/opengel/光照贴图`、`/cpp/boost/c++-boost` → 直接进页面，`title`/`h1` 正确、**无整页重载**（`window.__alive` 还在）、无 4xx、无 console 报错。
- `performance.getEntriesByType('resource')` 里 **sql_dump 请求 = 0**，`_payload.json` 请求正常 → 客户端确实不再碰那份库。
- 反例：把某页 `_payload.json` 改名后，**连硬刷新都会 404**（Nuxt 抛 `NUXT_E7002`）→ 说明 payload 必须与页面一起部署（同目录，天然同去同留）。

### 顺带查实
- `.output/public/__nuxt_content/content/sql_dump.txt` 由该模块的 `routeRules['/__nuxt_content/content/sql_dump.txt'] = { prerender: true }` 产出；
  `failOnError: false` 会让这条路由预渲染失败时**不报错**，旧文件继续留在服务器 → 正是本次故障的温床。
